# Test Server Auto Deploy Design

## Goal

Deploy `surge-screener` to the test server at `172.16.204.117` automatically whenever `main` is pushed to GitHub, with Streamlit reachable inside the private network at `http://172.16.204.117:8501`.

## Current Context

The repository runs a Streamlit app from `app.py`, with local development commands in `Makefile`. The existing GitHub workflow handles scheduled market scans and report commits, but there is no application deployment workflow. The test server accepts SSH as `kenny@172.16.204.117` via the `antigravity` SSH profile, has `git`, `curl`, `rsync`, `docker`, `nginx`, `systemd`, and Python `3.10.12`, but `/usr/bin/python3` has no system `pip` and `kenny` does not have passwordless sudo. User service lingering is enabled for `kenny`, so user-level systemd services can keep running after SSH sessions end.

## Deployment Architecture

The test server is on a private `172.16.x.x` address, so a public GitHub-hosted runner should not be assumed able to SSH into it. The first deployment version therefore uses a GitHub self-hosted runner installed on the test server. The runner polls GitHub for jobs, receives push-triggered deploy work, and executes deployment locally on `172.16.204.117`.

The deploy job keeps all runtime assets in the `kenny` user's home directory. It does not require sudo. The workflow checks out the pushed commit into the runner workspace, then runs `scripts/deploy_test_server.sh` locally on the test server. The script syncs the checked-out code to `/home/kenny/apps/surge-screener/current`, creates or reuses `/home/kenny/apps/surge-screener/.venv`, installs dependencies, installs DuckDB/Parquet support, writes a user-level `systemd` service, restarts Streamlit, and verifies the app with a local health check.

The Streamlit service binds to `0.0.0.0:8501` so clients on the private network can open `http://172.16.204.117:8501`. The health check uses `http://127.0.0.1:8501` from the test server because that validates the local service without depending on external routing.

## Components

- `.github/workflows/deploy_test_server.yml`: Runs on pushes to `main` and manual dispatch on a self-hosted runner labeled for this deployment target.
- `scripts/deploy_test_server.sh`: Idempotent local deploy script run by the self-hosted runner. It prepares directories, rsyncs the checked-out commit to the app directory, prepares the venv, installs dependencies, installs the user systemd unit, restarts the service, and performs health checks.
- `deploy/surge-screener.service`: User-level systemd unit template for the Streamlit app.
- `scripts/test_deploy_artifacts.py`: Offline validation for the workflow, deploy script, service template, and dependency declarations.
- `requirements.txt`: Adds `duckdb` and `pyarrow` so the deployed environment can support the planned DuckDB + Parquet factor-validation layer.

## Self-Hosted Runner Setup

The GitHub repository needs a self-hosted runner registered on the test server with labels:

```text
self-hosted
linux
x64
surge-screener-test
```

Runner registration requires a short-lived token from GitHub repository settings or the GitHub API. The local `gh` CLI is currently not authenticated, so that token must be generated by the user or after re-authenticating `gh`. The workflow itself does not need SSH secrets because it runs directly on the test server.

## Runtime Layout

```text
/home/kenny/actions-runner/

/home/kenny/apps/surge-screener/
  .venv/
  current/
    app.py
    requirements.txt
    data/
      sp500_ticker_start_end.csv
    reports/
  shared/
    data/
      parquet/
    analytics.duckdb

/home/kenny/.config/systemd/user/surge-screener.service
```

The service writes Streamlit runtime logs to the user journal, readable with:

```bash
ssh antigravity 'journalctl --user -u surge-screener -n 100 --no-pager'
```

## Data Layer Scope

This deployment only installs the DuckDB and Parquet dependencies. It does not yet migrate existing JSON reports to Parquet or change factor-validation logic. That keeps deployment risk separate from data-model work. A later change can add append-only Parquet writers and DuckDB query helpers under `data/`.

## Failure Handling

The deploy script is idempotent and uses `set -euo pipefail`, so a failed command stops deployment. It syncs only from the GitHub Actions checkout to the app directory and keeps the venv outside the app directory so deploys do not reinstall Python itself. If dependency installation, service restart, or health check fails, the GitHub Actions job fails and shows the failing step output.

The user service restarts automatically on failure with a short delay. The deploy script waits for Streamlit to respond locally before reporting success.

## Testing

Offline repo validation checks:

- Deploy workflow exists and is scoped to pushes on `main`.
- Workflow targets a self-hosted runner with the `surge-screener-test` label and runs the local deploy script.
- Deploy script contains strict shell settings, rsync-based checkout deployment, venv creation, dependency install, user systemd restart, and health check.
- Service template binds Streamlit to `0.0.0.0:8501`.
- `requirements.txt` includes `duckdb` and `pyarrow`.

Remote validation checks:

- `ssh antigravity 'python3 -V'`
- `ssh antigravity 'loginctl show-user kenny -p Linger'`
- `ssh antigravity 'systemctl --user status surge-screener --no-pager'`
- `curl -I http://172.16.204.117:8501`

## Out Of Scope

- PostgreSQL installation.
- Nginx reverse proxy, public domain, HTTPS, or authentication.
- Migrating reports or factor-validation outputs into Parquet.
- Running scheduled market scan jobs on the test server.
- Registering the self-hosted runner without a GitHub runner registration token.
